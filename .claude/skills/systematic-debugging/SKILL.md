# 체계적 디버깅

## 핵심 원칙

**근본 원인 조사 없이 절대 수정하지 마세요.**

증상만 가리는 임시 패치를 적용하지 마세요. 수정을 시도하기 전에 왜 실패하는지 이해하세요.

## 4단계 프레임워크

### 1단계: 근본 원인 조사

코드에 손대기 전:

1. **에러 메시지를 꼼꼼히 읽기** - 모든 단어가 중요
2. **이슈를 일관되게 재현하기** - 재현할 수 없으면 수정도 검증할 수 없음
3. **최근 변경 사항 확인** - 이 문제가 발생하기 전에 무엇이 바뀌었는가?
4. **진단 증거 수집** - 로그, 스택 트레이스, 상태 덤프
5. **데이터 흐름 추적** - 잘못된 값이 어디서 시작되는지 콜 체인 따라가기

**근본 원인 추적 기법:**
```
1. 증상 관찰 - 에러가 어디서 나타나는가?
2. 직접 원인 찾기 - 어떤 코드가 에러를 직접 발생시키는가?
3. "이것을 호출한 것은?" 질문 - 콜 체인을 위로 추적
4. 계속 위로 추적 - 잘못된 데이터를 스택을 거슬러 역추적
5. 최초 트리거 찾기 - 문제가 실제로 어디서 시작되었는가?
```

**핵심 원칙:** 에러가 나타나는 곳에서만 수정하지 말고 항상 최초 트리거까지 추적하세요.

### 2단계: 패턴 분석

1. **작동하는 예시 찾기** - 올바르게 작동하는 유사한 코드 찾기
2. **구현을 완전히 비교** - 대충 훑어보지 말기
3. **차이점 식별** - 작동하는 것과 고장난 것의 차이가 무엇인가?
4. **의존성 파악** - 이 코드가 무엇에 의존하는가?

### 3단계: 가설 및 테스트

과학적 방법 적용:

1. **명확한 가설 하나 수립** - "X 때문에 에러가 발생한다"
2. **최소 테스트 설계** - 한 번에 변수 하나만 변경
3. **결과 예측** - 가설이 맞다면 어떤 일이 일어나야 하는가?
4. **테스트 실행** - 실행하고 관찰
5. **결과 검증** - 예측대로 동작했는가?
6. **반복 또는 진행** - 틀렸으면 가설 수정, 맞으면 구현

### 4단계: 구현

1. **실패하는 테스트 케이스 작성** - 버그 동작을 포착
2. **단일 수정 적용** - 증상이 아닌 근본 원인 해결
3. **테스트 통과 확인** - 수정이 작동함을 확인
4. **전체 테스트 스위트 실행** - 회귀가 없는지 확인
5. **수정 실패 시 멈추기** - 가설 재평가

**중요 규칙:** 연속으로 세 번 이상 수정이 실패하면 멈추세요. 이는 패치가 아닌 논의가 필요한 아키텍처 문제를 나타냅니다.

## 위험 신호 - 프로세스 위반

다음과 같은 생각이 들면 즉시 멈추세요:

- "지금은 빠른 수정으로, 나중에 조사하자"
- "한 번만 더 수정해보자" (여러 번 실패 후)
- "이게 작동해야 할 텐데" (이유를 모르면서)
- "일단 해보자..." (가설 없이)
- "내 컴퓨터에서는 작동해" (차이를 조사하지 않고)

## 더 깊은 문제의 경고 신호

**다른 영역에서 새로운 문제를 계속 드러내는 연속적인 수정**은 아키텍처 문제를 나타냅니다:

- 패치 중단
- 발견한 것 문서화
- 진행 전 팀과 논의
- 설계를 재고할 필요가 있는지 고려

## 일반적인 디버깅 시나리오

### 테스트 실패

```
1. 전체 에러 메시지와 스택 트레이스 읽기
2. 어떤 단언이 실패했고 이유가 무엇인지 파악
3. 테스트 설정 확인 - 테스트 환경이 올바른가?
4. 테스트 데이터 확인 - 목/픽스처가 올바른가?
5. 예상치 못한 값의 출처 추적
```

### 런타임 에러

```
1. 전체 스택 트레이스 캡처
2. 예외가 발생하는 라인 파악
3. 어떤 값이 undefined/null인지 확인
4. 잘못된 값이 어디서 시작되었는지 역추적
5. 출처에 유효성 검사 추가
```

### "예전에는 작동했는데"

```
1. git bisect로 문제가 생긴 커밋 찾기
2. 이전 작동 버전과 변경 사항 비교
3. 어떤 가정이 바뀌었는지 파악
4. 가정 위반의 출처에서 수정
```

### 간헐적 실패

```
1. 경쟁 조건 찾기
2. 공유 가변 상태 확인
3. 비동기 작업 순서 검토
4. 타이밍 의존성 찾기
5. 결정론적 대기 또는 적절한 동기화 추가
```

## 디버깅 체크리스트

버그 수정을 완료했다고 주장하기 전:

- [ ] 근본 원인 파악 및 문서화
- [ ] 가설 수립 및 테스트
- [ ] 수정이 증상이 아닌 근본 원인 해결
- [ ] 버그를 재현하는 실패 테스트 작성
- [ ] 수정 후 테스트 통과
- [ ] 전체 테스트 스위트 통과
- [ ] "빠른 수정" 합리화 사용 안 함
- [ ] 수정이 최소화되고 집중적

## 성공 지표

체계적 디버깅은 즉흥적 접근법의 ~40% 대비 ~95%의 첫 번째 수정 성공률을 달성합니다.

올바르게 하고 있다는 신호:
- 수정이 새로운 버그를 만들지 않음
- 버그가 왜 발생했는지 설명할 수 있음
- 유사한 버그가 재발하지 않음
- 수정 후 코드가 단순히 "작동"하는 것보다 더 나아짐
